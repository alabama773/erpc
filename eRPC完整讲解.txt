================================================================
  eRPC 完整讲解（中文）
  —— 看懂这一份，就能跟老板交代 eRPC 是什么
================================================================


================================================================
  第 0 部分：一句话讲清 eRPC
================================================================

eRPC 是一个「容错的 EVM RPC 代理 + 永久缓存层」。

你把它架在你所有的 RPC 数据源（Alchemy、QuickNode、自建节点等）
前面，它自动帮你做：故障转移、重试、缓存、多链路由。

你的程序只需要连它「一个地址」，背后接了多少个数据源、
哪个坏了、要不要重试、能不能用缓存——它全帮你搞定。

官方原话：
"Stop babysitting RPC providers."
（别再当 RPC 服务商的保姆了。）


================================================================
  第 1 部分：为什么需要 eRPC？（它解决什么痛点）
================================================================

痛点：你的应用要读区块链数据，就得连 RPC 服务商。但——

  1. 服务商会挂：一个挂了，你的应用就断服务。
  2. 服务商会限流（rate limit）：请求多了就被拒。
  3. 同样的查询重复问：浪费钱（RPC 按调用量收费）。
  4. 多条链要接多个服务商：配置一堆、代码很乱。
  5. 有的节点数据是坏的/过时的：返回错误答案。

eRPC 一次性解决这五个问题：

  1. 挂了 → 自动换下一个数据源（failover 故障转移）
  2. 限流 → 自动重试 + 换源 + 自动调节请求速率
  3. 重复查询 → 缓存，问过一次直接给答案，不再花钱
  4. 多链 → 一个 URL 走所有链，加链不用改代码
  5. 坏数据 → 内置校验，坏的自动丢弃、换源重查


================================================================
  第 2 部分：eRPC 的核心功能（老板可能会问的）
================================================================

--- 2.1 Failover（故障转移）---
一个数据源失败，自动切到下一个。这是最核心的能力。

--- 2.2 Retry（重试）---
请求失败自动重试，可配置重试次数、延迟、退避、抖动。

--- 2.3 Hedge（对冲请求）---
某个数据源反应慢时，eRPC 悄悄同时向备用源发一个一样的请求，
谁先回用谁。你最慢的那些请求就「消失」了。

--- 2.4 Circuit Breaker（熔断器）---
某个数据源连续出错，自动把它「踢出」轮换，不再浪费请求给它；
等它恢复了再自动放回来。

--- 2.5 Consensus（共识）---
同一个请求同时问多个数据源，比对答案，取大家一致的那个，
自动标记/屏蔽「说谎」的节点。用于防止单个坏节点喂错数据。

--- 2.6 Integrity（完整性校验）---
自动丢弃「过时」或「结构损坏」的返回，换源重查，
保证调用方永远拿到正确答案。

--- 2.7 Caching（缓存 / 就是 db）---
把 RPC 返回结果按「区块最终性」分级缓存起来。
同一个查询下次直接从缓存拿，不再去问服务商。
★ 这个缓存就存在数据库里（内存/Redis/PostgreSQL/DynamoDB）
★ 老板说的 "db" 很可能就是指这个缓存数据库

--- 2.8 Rate Limit 自动调节 ---
eRPC 会根据错误率自动调整发给某个服务商的请求速率：
错误多了就放慢，健康了就加速。避免把服务商打到限流。

--- 2.9 Selection Policy（智能选源）---
每 15 秒根据「实时健康数据」给所有数据源打分，
最快最健康的优先用，坏的自动降权。


================================================================
  第 3 部分：关键限制（★ 这条最重要）
================================================================

【eRPC 只支持 EVM 链，不支持 Solana！】

- EVM 链 = 以太坊这一类的链，说的是同一种「语言」：
  以太坊(ETH)、BSC、Polygon、Arbitrum、Optimism 等等。
- eRPC 靠调用 eth_chainId 来识别链，整套缓存/路由/failover
  都是围绕 EVM 的 JSON-RPC 语义设计的。

- Solana 是【完全不同架构】的链，eRPC 听不懂。
  官方代码里搜「solana」一个字都没有。
  eRPC 配置里 type 字段的说明白纸黑字写着：
  "Only evm is supported at runtime"（运行时只支持 evm）。

★ 所以在我们的项目里：
    ETH / BSC → 用 eRPC（现成的，老板要的）
    Solana    → eRPC 做不了，必须在它外面单独写一套
                同样功能的 failover 层来「顶替」
  （这正是老板笔记里「solana 在外面找来顶替」的意思）


================================================================
  第 4 部分：怎么跑 eRPC（技术细节）
================================================================

--- 用什么写的 ---
Go 语言。编译成单个二进制，Docker 镜像约 30MB（distroless）。

--- 官方 Docker 镜像 ---
ghcr.io/erpc/erpc:latest

--- 启动命令 ---
docker run \
  -v $(pwd)/erpc.yaml:/erpc.yaml \
  -p 4000:4000 \
  -p 4001:4001 \
  ghcr.io/erpc/erpc:latest

或用 npx（需要 Node 18+）：
  npx @erpc-cloud/cli start ./erpc.yaml

--- 端口 ---
  4000 = JSON-RPC 请求入口
  4001 = Prometheus 监控指标

--- 配置文件 ---
  erpc.yaml（也支持 .yml / .ts / .js）
  启动时自动在当前目录 + /  + /root/ 里找，第一个匹配的生效。

--- 请求 URL 格式 ---
  /<项目>/<架构>/<链ID>
  以太坊主网:  http://localhost:4000/main/evm/1
  BSC:        http://localhost:4000/main/evm/56
  Arbitrum:   http://localhost:4000/main/evm/42161
  （加新链不用改配置，只要数据源支持）

--- 验证配置是否正确 ---
  docker run --rm -v $(pwd)/erpc.yaml:/erpc.yaml \
    ghcr.io/erpc/erpc:latest validate

--- 发一个请求测试 ---
  curl http://localhost:4000/main/evm/1 \
    -H "Content-Type: application/json" \
    -d '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}'


================================================================
  第 5 部分：配置文件 erpc.yaml 的结构
================================================================

顶层字段：
  logLevel      日志级别
  server        服务器设置（端口、TLS 等）
  metrics       监控指标设置
  database      ★ 缓存数据库设置（就是 db）
  projects      项目（一个 eRPC 可服务多个项目/租户）
  rateLimiters  限流预算
  proxyPools    代理池

每个 project 里：
  upstreams     数据源（具体的 RPC 端点）
  providers     服务商（一个 key 自动生成多链数据源，内置23家）
  networks      每条链的设置 + failsafe 规则
  auth          认证（token / JWT / 钱包签名 / IP 白名单）
  cors          浏览器跨域设置

failsafe（容错）规则可配在 upstream 或 network 层：
  retry           重试
  hedge           对冲
  timeout         超时
  circuitBreaker  熔断
  consensus       共识
  integrity       完整性校验


================================================================
  第 6 部分：db（数据库）在 eRPC 里是什么
================================================================

eRPC 的 database 就是它的「缓存后端」。

作用：把 RPC 查询的结果存起来，同样的查询下次直接从库里拿，
不用再花钱去问 RPC 服务商。这是 eRPC「永久缓存层」的核心。

支持 5 种存储后端：
  1. memory      内存（重启就没了，适合测试）
  2. Redis       内存数据库（快，适合缓存）
  3. PostgreSQL  关系型数据库（持久，适合长期缓存）
  4. DynamoDB    亚马逊云数据库
  5. gRPC BDS    只读的 gRPC 连接器

缓存怎么分级：
  按「区块最终性」分桶——已确认的老区块结果可以永久缓存，
  链头附近可能变动的数据会拒绝返回过时结果。

★ 我们现在的 eRPC 配置【默认没开 db 缓存】。
  如果老板要的「db」是指这个，我可以加：
  在 erpc.yaml 里加 database 配置 + 起一个 Redis 或 Postgres。


================================================================
  第 7 部分：内置服务商（providers）
================================================================

eRPC 内置 23 家 EVM 服务商集成，用「一个 key 走该商所有链」。
例如配一行 alchemy://你的key，它自动为该商支持的每条链
生成数据源。

还有一个特殊的免费服务商 "repository"：
  它从 eRPC 官方拉取「免费公共端点」目录，按链自动生成数据源，
  完全不需要 API key。
  ★ 我们项目现在用的就是这个（所以 ETH/BSC 不用 key 也能跑）。


================================================================
  第 8 部分：监控与可观测性
================================================================

- 端口 4001 暴露 Prometheus 指标（共 122 个指标）。
- 官方带一个 Grafana 仪表盘（80+ 面板），涵盖：
  请求量、延迟、故障转移事件、共识、缓存命中、限流、区块延迟等。
- 5 条内置告警规则：高错误率、慢请求、高限流、网络限流、请求量异常。


================================================================
  第 9 部分：一句话总结（背下来能应付老板）
================================================================

eRPC = 一个用 Go 写的、跑在 Docker 里的「EVM RPC 智能代理」。

它接在多个 RPC 服务商前面，自动做故障转移、重试、对冲、熔断、
缓存（存在 db 里）、多链路由。你的程序只连它一个地址就行。

它【只支持 EVM 链】（ETH/BSC 等），【不支持 Solana】——
所以 Solana 必须在 eRPC 外面单独做一套 failover 层顶替。

在我们的项目里：
  ETH / BSC → eRPC（端口 4000）
  Solana    → 自建 failover 层（端口 4100）
  db        → eRPC 的缓存数据库（可选 Redis/Postgres，目前未开）
